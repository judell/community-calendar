# Findings

## F001 Fresh local and upstream Davis builds matched on aggregate outputs

The fresh local run and upstream job converged on the same aggregate results:

- `combined.ics`: `640` events
- `events.json`: `640` events
- RSS: `full=611 latest=97`

That parity is important because it means the remaining work is mostly about source health and audit quality, not local-vs-remote drift.

## F002 Davis Chamber scraper resolves to no events because the chamber host is unreachable

Both runs logged repeated connection failures against `web.davischamber.com` across all requested months, then wrote an empty `cities/davis/davis_chamber.ics`.

Follow-up: completed on 2026-08-06. The scraper was retired and the Davis sources checklist now records the source as removed because the upstream host no longer resolves.

## F003 UU Davis scraper still references a dead Google Calendar feed

Both runs logged a `404` for one Google Calendar URL inside the UU Davis scraper, but the scraper still emitted `2311` raw events and `11` future events survived combination.

Follow-up: completed on 2026-08-06. The dead Google Calendar sub-feed was removed from the scraper.

## F004 UC Davis Arts produced zero events because of malformed DTSTART values

Both runs logged repeated warnings about malformed `DTSTART` values such as `20260929Z`, then produced an empty `ucdavis_arts.ics`.

Follow-up: completed on 2026-08-06. The scraper was hardened to normalize the malformed all-day dates, and the Davis sources checklist records that fix.

## F005 UC Davis Library produced zero events in both runs without surfacing a hard error

In the fresh parity run, both local and upstream builds produced an empty `ucdavis_library.ics` with no hard transport error. That differs from the earlier transient `429` seen in a previous local run, so the current evidence says "zero events today" rather than "definite fetch failure."

This one may require human judgment if the source legitimately has no current events. The procedure should let an agent flag it for verification rather than forcing a binary broken/not-broken decision.

## F006 The audit tooling underreports scraper failures and accepts broken zero-event scrapers as healthy

The procedure found the real problems, but not cleanly:

- upstream job reported `Build errors found: 5`
- fresh local report recorded only `1` build error
- validation still reported `0 errors, 0 warnings`
- local report counted `4` empty live feeds but did not escalate the empty workflow scrapers

This is the main procedure gap. The report is already good enough to drive source cleanup, but not yet good enough to let an agent trust the summary fields without reading raw logs.

Follow-up: completed on 2026-08-07. The local audit runner now records structured build issues, distinguishes zero-event scraper outputs from live-feed empties, and emits an action report.
